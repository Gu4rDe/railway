# Генерация UML через PlantUML

Цель: диаграмма должна быть **корректной по нотации UML** и **читаемой с первого взгляда**. «Кривая» диаграмма почти всегда получается из-за трёх вещей: нет настроек раскладки, слишком много элементов на одном листе, перепутаны виды связей. Скилл закрывает все три.

## Порядок работы

1. **Определи тип диаграммы.** Если пользователь не сказал, выбери по смыслу: структура → классы/компоненты, поведение во времени → последовательность, сценарии пользователя → варианты использования, алгоритм → активность, жизненный цикл объекта → состояния, данные БД → ER (через классы или `entity`).
2. **Ограничь объём.** Один лист — одна идея. Не больше 8–10 элементов (классов, компонентов, состояний) и 12–15 сообщений на sequence-диаграмму. Если материала больше, разбей на несколько диаграмм (по модулям или слоям) и скажи об этом.
3. **Собери код по шаблону** из `references/templates.md` для нужного типа: готовая «шапка» с настройками плюс каркас.
4. **Проверь нотацию** по чеклисту ниже.
5. **Отрисуй и посмотри результат** (раздел «Рендер и проверка» ниже). Если рендерить нечем, выдай код и честно скажи, что рендер не проверялся.
6. **Исправь визуальные дефекты** (см. «Лечение кривизны») и только потом отдавай результат.

## Почему важна «шапка»

Без неё PlantUML рисует связи кривыми линиями, плотно прижимает элементы и добавляет тени и пустые блоки. Поэтому всегда начинай с базовых настроек (полные наборы для каждого типа — в `references/templates.md`):

```plantuml
skinparam linetype ortho
skinparam nodesep 60
skinparam ranksep 60
skinparam shadowing false
skinparam roundcorner 8
skinparam dpi 150
hide empty members
```

Если пользователь делает отчёт или печатает чёрно-белым (типично для учебных работ), добавь `!theme plain` или `skinparam monochrome true`. Цвета на печати теряются, а читаемость остаётся.

## Нотация: что чаще всего путают

| Связь | PlantUML | Смысл |
|---|---|---|
| Наследование | `Child --|> Parent` | Child расширяет Parent (треугольник у Parent) |
| Реализация | `Impl ..|> Interface` | класс реализует интерфейс (пунктир) |
| Ассоциация | `A --> B` | A знает о B и использует его как поле |
| Агрегация | `Whole o-- Part` | часть живёт независимо от целого (ромб у целого) |
| Композиция | `Whole *-- Part` | часть умирает вместе с целым (закрашенный ромб у целого) |
| Зависимость | `A ..> B` | A использует B временно (параметр, локальная переменная) |

Правила, которые нужно соблюдать:

- **Кратность** указывай там, где она важна: `A "1" --> "0..*" B : содержит`. Подписывай связь глаголом.
- **Видимость**: `+` public, `-` private, `#` protected, `~` package. Атрибуты пиши как `-name : String`, методы как `+getName() : String`.
- **Абстрактные классы** и **интерфейсы** объявляй явно: `abstract class X`, `interface Y`. Это даёт правильное оформление (курсив, `<<interface>>`).
- **Не смешивай уровни.** На диаграмме классов не рисуй вызовы методов, на sequence не рисуй наследование.
- **Не дублируй** связи. Если есть наследование, не добавляй ещё и ассоциацию между теми же классами.
- **Язык подписей** — язык пользователя (русский для русскоязычного). Идентификаторы классов и методов оставляй такими, как в коде. Для русских подписей с пробелами используй кавычки: `class "Заказ" as Order`.

## Лечение кривизны

Когда диаграмма получилась неаккуратной, иди по списку сверху вниз, останавливаясь на первом помогшем шаге:

1. **Связи перекрещиваются** → задай направления: `A -down-> B`, `A -right-> B`. Главные классы поставь вверху, зависимые под ними.
2. **Подписи на связях съехали** (бывает при `ortho`) → замени на `skinparam linetype polyline` или сократи подписи.
3. **Элементы слиплись** → увеличь `nodesep` и `ranksep` (80–100).
4. **Диаграмма вытянулась в одну сторону** → переключи `left to right direction` или обратно, либо разбей на две.
5. **Связанные элементы разбросаны** → объедини их: `package "Модуль" { ... }` или `together { A  B }`.
6. **Нужно принудительно выровнять** → невидимая связь: `A -[hidden]down-> B`.
7. **Всё ещё плохо** → смени движок: `!pragma layout elk` (если доступен). Если нет, упрости диаграмму: убери второстепенные классы.

## Рендер и проверка

Синтаксически верный код ещё не значит аккуратную диаграмму, поэтому всегда смотри на картинку. Если есть доступ к bash, рендери локально, это быстрее и надёжнее любого MCP:

```bash
which java dot                      # нужны Java и Graphviz (dot)
curl -sL -o /tmp/plantuml.jar \
  https://github.com/plantuml/plantuml/releases/download/v1.2025.4/plantuml-1.2025.4.jar
java -jar /tmp/plantuml.jar -charset UTF-8 -tpng diagram.puml   # PNG
java -jar /tmp/plantuml.jar -charset UTF-8 -tsvg diagram.puml   # SVG
```

Ключ `-charset UTF-8` обязателен для кириллицы. Затем открой PNG инструментом просмотра изображений и оцени результат по чеклисту ниже. Если доступен только PlantUML MCP, рендери им и тоже смотри на результат.

Правила итераций:
- Делай не больше 2–3 итераций правок. После каждой сравнивай с предыдущей версией.
- **Если правка ухудшила раскладку, откатись** к прошлой версии и вноси более мягкую правку. Не наслаивай исправления друг на друга.
- Сначала пробуй простые меры (настройки, порядок объявления, размеры отступов) и только потом принудительные.

## Если пользователь прислал картинку диаграммы

Это частый случай: образец уже есть, но выглядит неаккуратно. Не пытайся «исправить» его на глаз, а воспроизведи заново:

1. **Выпиши словами** всё, что видишь: актёров, группы или пакеты (с их названиями), каждый элемент внутри групп, каждую связь с типом (ассоциация, обобщение, include/extend, зависимость) и направлением.
2. **Сохрани содержание**: те же названия, те же группы, те же связи. Не добавляй и не выбрасывай элементы без согласия пользователя. Исключение — явные ошибки нотации. О них скажи отдельно.
3. Собери код по шаблону, отрендери, сверь с исходником по списку из шага 1.
4. В ответе перечисли, что изменилось, и честно назови оставшиеся недостатки раскладки.
5. **Не добавляй связи, которых нет на образце**, в частности `<<include>>` и `<<extend>>`. Если пользователь сказал, что они лишние или на образце их нет, не рисуй их. Если связей много и получается «пучок», предложи упрощение, а не усложняй диаграмму.

Готовый разобранный пример (диаграмма вариантов использования «Железная дорога» по образцу с актёром-родителем, без `include`) — в `references/examples.md`. Читай его, когда нужно воспроизвести похожую диаграмму с группами.

## Уроки из практики

- **Заголовок группы налезает на элемент внутри.** Особенно у маленьких групп с одним элементом. Добавь в конец названия **две** перевода строки: `rectangle "Общий доступ\n\n" as G4 { ... }`. Один `\n` или пробел PlantUML обрезает, и эффекта нет.
- **Сторона элемента определяется порядком записи связи, а не стрелкой.** `L <.. A1` и `A1 ..> L` — одна и та же связь, но в раскладке левый элемент записи идёт раньше. Хочешь элемент слева — ставь его слева в записи. Это основной способ управлять положением без хаков. Если пользователь просит «чтобы X был слева/справа», сначала подумай, какие линии при этом пересекутся. Часто выгоднее переставить и актёров (например, вправо), чтобы не было пересечений, и сказать об этом.
- **Невидимые связи** (`-[hidden]->`) нужны, но только правильного направления и только между нужными элементами. Между блоками групп (`G1 -[hidden]down-> G2`) и с `[norank]` они ломали раскладку, пришлось откатываться. А вот чтобы расставить актёров в нужном вертикальном порядке при `left to right direction`, работает `-[hidden]right->` (PlantUML поворачивает направления, поэтому `down` и `up` здесь не работают). Всегда проверяй рендером, а порядок элементов на картинке при необходимости проверяй по SVG.
- **Порядок объявления** слабо влияет на вертикальный порядок: в одном эксперименте ни одна из 6 перестановок не дала нужный порядок актёров. Можно попробовать, но если не вышло, сразу переходи к невидимым связям между актёрами.
- **`skinparam linetype ortho`** не всегда помогает. Когда много связей сходится в один элемент, ortho склеивает их в одну линию и накладывает подписи. Проверяй рендером и откатывайся к обычным линиям.
- **Много связей в одну цель** собираются в пучок, и чем их больше, тем хуже читается диаграмма. Поэтому не добавляй связи, которых нет в образце или в задании (особенно `include`/`extend`). Если пучок всё же нужен, увеличь `ranksep` до 110–120 и сократи подписи.
- **Многострочные названия.** В овалах и блоках переноси длинные названия через `\n` (две строки по 15–20 символов), иначе элементы растягиваются.
- **Обобщение актёров**: `Клиент -up-|> Пользователь`. Стрелка идёт от потомка к родителю, треугольник у родителя.

## Чеклист перед выдачей

- [ ] Код начинается с `@startuml` и заканчивается `@enduml`, скобки `{}` сбалансированы.
- [ ] Есть «шапка» с настройками раскладки.
- [ ] Виды стрелок соответствуют смыслу связи (таблица выше).
- [ ] У ключевых связей есть кратность и подпись.
- [ ] Не больше 8–10 элементов на диаграмме.
- [ ] Нет «висящих» элементов без единой связи (если это не намеренно).
- [ ] Подписи читаются, язык согласован.
- [ ] Если рендер выполнялся, диаграмма просмотрена глазами, а не только «собралась без ошибок».
- [ ] Если пользователь прислал образец, ничего из него не потеряно (сверено по списку).
- [ ] Ни один заголовок группы не налезает на элементы, ни одна подпись не лежит на чужой линии.
- [ ] Оставшиеся недостатки названы в ответе, а не скрыты.

## Mermaid как запасной вариант

Если PlantUML недоступен или диаграмму нужно вставить в Markdown/GitHub, используй Mermaid (`classDiagram`, `sequenceDiagram`, `flowchart`, `stateDiagram-v2`). Те же правила: ограничение объёма, корректные виды связей, подписи. Нотацию связей Mermaid смотри в конце `references/templates.md`.
