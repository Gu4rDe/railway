# Генерация UML через PlantUML

Цель: диаграмма должна быть **корректной по нотации UML** и **читаемой с первого взгляда**. «Кривая» диаграмма почти всегда получается из-за трёх вещей: нет настроек раскладки, слишком много элементов на одном листе, перепутаны виды связей. Скилл закрывает все три.

## Порядок работы

1. **Определи тип диаграммы.** Если пользователь не сказал, выбери по смыслу: структура → классы/компоненты, поведение во времени → последовательность, сценарии пользователя → варианты использования, алгоритм → активность, жизненный цикл объекта → состояния, данные БД → ER (через классы или `entity`).
2. **Ограничь объём.** Один лист — одна идея. Не больше 8–10 элементов (классов, компонентов, состояний) и 12–15 сообщений на sequence-диаграмму. Если материала больше, разбей на несколько диаграмм (по модулям или слоям) и скажи об этом.
3. **Собери код по шаблону** из `references/templates.md` для нужного типа: готовая «шапка» с настройками плюс каркас.
4. **Проверь нотацию** по чеклисту ниже.
5. **Отрисуй и посмотри результат**, если есть инструмент рендера (PlantUML MCP или локальный `plantuml`). Если рендерить нечем, выдай код и честно скажи, что рендер не проверялся.
6. **Исправь визуальные дефекты** (см. «Лечение кривизны») и только потом отдавай результат.

## Почему важна «шапка»

Без неё PlantUML рисует связи кривыми линиями, плотно прижимает элементы и добавляет тени и пустые блоки. Поэтому всегда начинай с базовых настроек (полные наборы для каждого типа — в `references/templates.md`):

```plantuml
skinparam linetype ortho
skinparam nodesep 60
skinparam ranksep 60
skinparam shadowing false
skinparam roundcorner 8
skinparam dpi 150
hide empty members
```

Если пользователь делает отчёт или печатает чёрно-белым (типично для учебных работ), добавь `!theme plain` или `skinparam monochrome true`. Цвета на печати теряются, а читаемость остаётся.

## Нотация: что чаще всего путают

| Связь | PlantUML | Смысл |
|---|---|---|
| Наследование | `Child --|> Parent` | Child расширяет Parent (треугольник у Parent) |
| Реализация | `Impl ..|> Interface` | класс реализует интерфейс (пунктир) |
| Ассоциация | `A --> B` | A знает о B и использует его как поле |
| Агрегация | `Whole o-- Part` | часть живёт независимо от целого (ромб у целого) |
| Композиция | `Whole *-- Part` | часть умирает вместе с целым (закрашенный ромб у целого) |
| Зависимость | `A ..> B` | A использует B временно (параметр, локальная переменная) |

Правила, которые нужно соблюдать:

- **Кратность** указывай там, где она важна: `A "1" --> "0..*" B : содержит`. Подписывай связь глаголом.
- **Видимость**: `+` public, `-` private, `#` protected, `~` package. Атрибуты пиши как `-name : String`, методы как `+getName() : String`.
- **Абстрактные классы** и **интерфейсы** объявляй явно: `abstract class X`, `interface Y`. Это даёт правильное оформление (курсив, `<<interface>>`).
- **Не смешивай уровни.** На диаграмме классов не рисуй вызовы методов, на sequence не рисуй наследование.
- **Не дублируй** связи. Если есть наследование, не добавляй ещё и ассоциацию между теми же классами.
- **Язык подписей** — язык пользователя (русский для русскоязычного). Идентификаторы классов и методов оставляй такими, как в коде. Для русских подписей с пробелами используй кавычки: `class "Заказ" as Order`.

## Лечение кривизны

Когда диаграмма получилась неаккуратной, иди по списку сверху вниз, останавливаясь на первом помогшем шаге:

1. **Связи перекрещиваются** → задай направления: `A -down-> B`, `A -right-> B`. Главные классы поставь вверху, зависимые под ними.
2. **Подписи на связях съехали** (бывает при `ortho`) → замени на `skinparam linetype polyline` или сократи подписи.
3. **Элементы слиплись** → увеличь `nodesep` и `ranksep` (80–100).
4. **Диаграмма вытянулась в одну сторону** → переключи `left to right direction` или обратно, либо разбей на две.
5. **Связанные элементы разбросаны** → объедини их: `package "Модуль" { ... }` или `together { A  B }`.
6. **Нужно принудительно выровнять** → невидимая связь: `A -[hidden]down-> B`.
7. **Всё ещё плохо** → смени движок: `!pragma layout elk` (если доступен). Если нет, упрости диаграмму: убери второстепенные классы.

## Чеклист перед выдачей

- [ ] Код начинается с `@startuml` и заканчивается `@enduml`, скобки `{}` сбалансированы.
- [ ] Есть «шапка» с настройками раскладки.
- [ ] Виды стрелок соответствуют смыслу связи (таблица выше).
- [ ] У ключевых связей есть кратность и подпись.
- [ ] Не больше 8–10 элементов на диаграмме.
- [ ] Нет «висящих» элементов без единой связи (если это не намеренно).
- [ ] Подписи читаются, язык согласован.
- [ ] Если рендер выполнялся, диаграмма просмотрена глазами, а не только «собралась без ошибок».

## Mermaid как запасной вариант

Если PlantUML недоступен или диаграмму нужно вставить в Markdown/GitHub, используй Mermaid (`classDiagram`, `sequenceDiagram`, `flowchart`, `stateDiagram-v2`). Те же правила: ограничение объёма, корректные виды связей, подписи. Нотацию связей Mermaid смотри в конце `references/templates.md`.
